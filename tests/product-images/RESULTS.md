# Результаты оптимизации изображений

## Что реализовано

- единый FSD-компонент responsive image с независимыми состояниями loading, loaded, error и missing;
- нейтральный skeleton вместо логотипа во время обычной загрузки;
- продуктовые профили для карточки, hero-изображения модалки и миниатюр;
- корректные width-дескрипторы, равные фактической ширине файлов;
- WebP с JPEG fallback без предварительной загрузки логотипа;
- lazy loading карточек и миниатюр, eager/high priority только для открытого hero-изображения модалки;
- unit-тесты контракта, read-only аудит CDN, локальный benchmark кодирования и Chrome E2E/visual regression.

Изменения выполнены только в новой FSD/Storybook-части. Legacy-приложение в `modules/**`, production CDN и Object Storage не изменялись.

## Подтверждённый выбор ресурсов

Chrome-проверки выполнены при DPR 2:

| Сценарий                        | CSS-ширина | Выбранный ресурс |
| ------------------------------- | ---------: | ---------------: |
| Карточка, viewport 500          |     126 px |      366 px WebP |
| Карточка, viewport 800          |     202 px |      466 px WebP |
| Карточка, viewport 1400         |     303 px |      732 px WebP |
| Hero модалки, viewport 500      |     500 px |     1168 px WebP |
| Миниатюра состава, viewport 500 |     200 px |      466 px WebP |

Для карточек кандидат покрывает `CSS width × DPR`, а запас не превышает 1,5 раза. Этот контракт закреплён в Playwright.

## Read-only аудит CDN

Контрольный запуск:

```bash
npm run images:audit -- --id Madeira_set --output /tmp/jaco-image-audit.json
```

Результат:

- 14 `HEAD`-запросов;
- 12 вариантов доступны;
- WebP и JPEG 875 px отсутствуют;
- существующие WebP возвращают `Content-Type: application/octet-stream`;
- JPEG возвращают корректный `Content-Type: image/jpeg`.

Поэтому 875 px исключён из frontend-manifest до миграции исторических объектов. Добавлять новый bucket в `srcset` можно только после аудита репрезентативной выборки каталога.

## Локальный benchmark

Smoke-запуск выполнен на одном контрольном изображении шириной 366 px. Отчёт сравнивает варианты с WebP quality 90 того же размера.

| Вариант  |       Размер | Экономия |     PSNR | Кодирование |
| -------- | -----------: | -------: | -------: | ----------: |
| WebP q75 |  24 450 байт |   40,11% | 28,68 dB |    56,73 мс |
| WebP q80 |  28 820 байт |   29,41% | 29,31 dB |    82,39 мс |
| WebP q85 |  34 022 байт |   16,67% | 29,93 dB |    80,55 мс |
| WebP q90 |  40 828 байт | baseline | 30,35 dB |    77,53 мс |
| AVIF q55 |  19 228 байт |   52,90% | 29,41 dB | 1 165,33 мс |
| AVIF q65 | 26 002 байта |   36,31% | 31,45 dB | 1 492,25 мс |

Это smoke, а не основание менять production quality. Перед таким решением нужен прогон на 10–20 оригиналах разных категорий и ручная слепая проверка. Повторно сжатый CDN-файл не заменяет оригинал.

## Автоматические проверки

```bash
npm run test:images
IMAGE_STORYBOOK_URL=http://localhost:6008 npm run test:images:e2e
```

Подтверждено:

- unit: 11 тестов пройдены;
- Chrome E2E: 6 тестов пройдены;
- responsive matrix: 500, 800 и 1400 px при DPR 2;
- skeleton видим до завершения задержанного image request;
- после загрузки skeleton удаляется;
- при ошибке показывается fallback без промежуточного логотипа;
- hero и thumbnail используют разные профили;
- visual snapshots маскируют содержимое remote image и проверяют только устойчивую геометрию UI.

## Известные ограничения

- `transferSize` и `encodedBodySize` cross-origin ресурсов могут быть пустыми, пока CDN не отдаёт `Timing-Allow-Origin`; точные байты берутся из read-only аудита.
- Production-like `storybook build` блокируется существующей ошибкой интеграции Next/Storybook при разборе вывода TypeScript `--showConfig`. Dev Storybook работает после настройки JSX loader, поэтому Chrome-проверки выполнены. Build-блокер следует исправить отдельной инфраструктурной задачей, не смешивая его с image contract.
- FSD-компоненты не изменяют текущую legacy-страницу. Для переноса улучшения в production требуется следующий утверждённый этап redesign либо явное разрешение на legacy-адаптер.
- S3/Object Storage не изменялся; upload/purge/invalidation отсутствуют намеренно.

## Следующее решение

Техническому лиду нужно выбрать:

1. подключать реализованный FSD-компонент при штатном переносе страницы на новую архитектуру;
2. разрешить отдельную минимальную интеграцию этого же контракта в legacy-компоненты текущего сайта;
3. после benchmark на оригиналах выбрать, оставлять WebP q90 или снижать quality/добавлять AVIF;
4. исправить metadata WebP и определить стратегию миграции отсутствующего 875px bucket.
