# QR-форма отзыва о чистоте кафе

## Маршруты и ссылка

Форма доступна по двум городонезависимым SSR-маршрутам:

```text
/feedback/stars/{token}
/feedback/emoji/{token}
```

Оба маршрута используют один динамический контракт и один сценарий; различается
только селектор оценки и передаваемый `ui_variant` (`stars` или `emoji`).
Действующие ссылки восьми кафе и команды их генерации собраны в
[`cafe-feedback-links.md`](./cafe-feedback-links.md).
Интерфейс имеет отдельные варианты для Mobile (320–667 px), Tablet (668–990 px)
и Desktop (991+ px).

Многоразовый токен относится только к точке кафе. Это зашифрованный AES-256-GCM
envelope в lowercase Base32 (`a-z`, `2-7`) длиной до 2048 символов. Ссылка не
содержит пользователя или конкретный отзыв; её можно отозвать на backend.
Некорректный токен и выключенный feature flag дают `404`.

## Переменные окружения

```dotenv
# Серверный флаг. Не попадает в браузерный bundle.
CAFE_FEEDBACK_PAGE_ENABLED=true

# Публичный endpoint формы. Значение ниже также используется по умолчанию.
NEXT_PUBLIC_CAFE_REVIEW_API_URL=https://api2.jacochef.ru/site/public/index.php/cafe_review
```

После изменения env нужно перезапустить Next.js. В публичном контракте нет
телефона, SMS, CAPTCHA и соответствующих клиентских переменных.

## Сценарий

1. Браузер создаёт случайный 128-битный `browser_id`, сохраняет его в
   `localStorage`, синхронизирует с host-only cookie для пути `/feedback` и
   передаёт во всех запросах как multipart-поле. Значение из `localStorage`
   имеет приоритет; cookie восстанавливает его после очистки хранилища.
2. `get_form` возвращает правила оценок и каталог причин из БД. Полученный
   каталог фиксируется backend в сессии, поэтому последующая публикация новой
   версии не меняет уже открытую форму.
3. Выбор оценки вызывает `start_review` и сохраняет частичный отзыв.
4. Для оценок 1–4 требуется хотя бы одна доступная для оценки причина из БД.
   Фотография обязательна, если у любой выбранной причины
   `photo_requirement=required`; комментарий необязателен. Завершение создаёт
   инцидент со статусом `new`, начальным событием и без severity.
5. Для оценки 5 доступен только необязательный комментарий: причины и
   фотографии не передаются, инцидент не создаётся.
6. `complete_review` завершает отзыв. Автоматического повтора мутаций нет; при
   ручном повторе сохраняется тот же `idempotency_key`.

## Контракт браузера

Все запросы — `POST multipart/form-data` напрямую на
`NEXT_PUBLIC_CAFE_REVIEW_API_URL`, с `type`, `token` и `browser_id`. Общая
HMAC-подпись сайта не используется. Backend хранит только HMAC от
`browser_id`.

### `get_form`

Запрос: `type=get_form`, `token`, `browser_id`.

Ответ: `st`, `cafe`, `server_date`, `form_token`, `catalog_version`,
`catalog_hash`, `rating_rules`, `issues`, `limits`. В `rating_rules` приходят
`rating`, `scenario`, флаги отображения секций и `creates_incident`; в
`issues` — `code`, `label`, `ratings`, `is_other` и `photo_requirement`.
Frontend соблюдает серверные `limits.max_photos`, `limits.max_photo_bytes` и
`limits.max_issues`. Текущая конфигурация разрешает до четырёх фотографий по
35 МБ. При пакетном выборе frontend рассматривает только первые доступные по
количеству файлы, пропускает неподдерживаемые форматы и превышение размера,
но сохраняет остальные допустимые фотографии.

### `start_review`

Запрос: `type=start_review`, `token`, `browser_id`, `form_token`,
`ui_variant`, `rating`, `idempotency_key`, `honeypot`, `time_on_page_ms`.

Ответ: `st`, `status`, `review_token`, `idempotent`.

### `complete_review`

Запрос: `type=complete_review`, `token`, `browser_id`, `form_token`,
`review_token`, `idempotency_key`, `rating`, `ui_variant`, JSON-массив
`issues`, `issue_other`, `comment`, при допустимом сценарии — `photos[]`.

Ответ: `st`, `status`, `idempotent`, `scenario`, `incident_created`.
Идемпотентный replay распознаётся до проверки cooldown и загрузки файлов.

## Ограничения и ошибки

Высокий технический Redis rate limit запросов отделён от десятиминутного
скользящего MySQL cooldown успешной отправки для пары браузер–точка. Ответ
`429` содержит `retry_after` в секундах и заголовок `Retry-After`.
Семантический cooldown дополнительно содержит точный
`code=review_already_submitted`. Только сочетание этого кода, статуса `429` и
положительного `retry_after` показывает существующий экран успешного
сохранения без таймера. Технический `429`, сетевая ошибка и неполный или
повреждённый успешный ответ экран благодарности не показывают.

Cookie имеет `Path=/feedback`, `Max-Age=31536000`, `SameSite=Lax`, а `Secure`
добавляется только по HTTPS; атрибут `Domain` не задаётся. Запись
`localStorage` и cookie выполняется независимо, при блокировке обоих
идентификатор живёт только в памяти вкладки. Запрос к API сохраняет
`credentials=omit`, поэтому cookie не отправляется на cross-origin endpoint.

- `401` и `404` — ссылка или сессия недействительна;
- `409` — конфликт повторной отправки;
- `422` — ошибка контракта или заполнения;
- `429` — превышен технический лимит или действует cooldown;
- сетевые и остальные ошибки — безопасное сообщение с ручным повтором там,
  где он допустим.

Неактивная точка показывается отдельным конечным состоянием.

## Безопасность и индексация

SSR-ответы устанавливают:

- `Cache-Control: private, no-store, max-age=0`;
- `X-Robots-Tag: noindex, nofollow`;
- `Referrer-Policy: no-referrer`;
- `X-Frame-Options: DENY`.

В `<head>` также присутствует `robots=noindex,nofollow`. Маршруты не
добавляются в навигацию и sitemap. `robots.txt` не закрывает их от обхода,
чтобы робот мог увидеть `noindex`.

## Проверка

```bash
npm run build
```

Проверяются оба варианта (`stars`, `emoji`) на Mobile, Tablet и Desktop.
Проверки состояния с подменами не заменяют smoke-тест на мигрированной MySQL и
реальном приватном S3.

## RELEASE BLOCKER: утечка токена в мониторинг

До production-включения маршрутов выпуск заблокирован. Глобальная Яндекс
Метрика в `pages/_app.js` и Sentry в `instrumentation-client.js` получают
полный многоразовый URL вместе с токеном.

Перед релизом необходимо отдельной задачей:

1. исключить `/feedback/stars/**` и `/feedback/emoji/**` из клиентского
   мониторинга либо гарантированно редактировать токен до отправки URL;
2. перевыпустить все тестовые QR-ссылки, токены которых уже могли попасть в
   Метрику, Sentry, логи или историю браузера;
3. подтвердить, что новые события и ошибки не содержат многоразовый токен.

Эта блокировка намеренно остаётся вне текущего объёма: изменения
`pages/_app.js` и `instrumentation-client.js` здесь запрещены.
