# TASK: динамические текстовые страницы сайта

## Контекст

В городском разделе сайта (`/{city}/...`) каждая текстовая CMS-страница сейчас представлена отдельным файлом Next.js в `pages/[city]/`. Это создаёт повторяющийся код, хотя содержимое страницы уже запрашивается по slug из API.

Пользователь хочет, чтобы обычные текстовые страницы открывались по динамическому маршруту вида `/{city}/{page}` без отдельного файла для каждого нового slug. Страница «О нас» должна остаться особым случаем.

## Цель

Подготовить безопасный план перехода на общий динамический маршрут текстовых страниц с сохранением существующего поведения сайта, SEO и старых URL.

## Ограничения

- Не менять backend-контракт и схему БД. Изменение production-данных запрещено; локальную БД можно дополнить CMS-данными только для браузерной проверки и по отдельному запросу владельца.
- Не менять разметку, порядок блоков, визуальные компоненты, брейкпоинты, адаптивные единицы и размеры; UI должен остаться визуально прежним. Допустимы только явно запрошенные владельцем scoped-правки оформления таблицы условий хранения и ссылки «На главную» на 404, отражённые в `PLAN.md`.
- Сохранять стиль и соглашения текущего Pages Router/legacy-кода, не вводить несвязанные архитектурные миграции.
- Коммитить крупные, законченные этапы в формате `feat|fix|refactor|docs: краткое описание`.
- Не объединять страницу «О нас» с обычным текстовым шаблоном без отдельного решения.

## Критерии готовности реализации

- Новый текстовый slug, имеющий данные в CMS, открывается без создания отдельного файла страницы.
- Существующие текстовые URL, заголовки, метаданные, ссылки, нижний колонтитул и особые варианты отображения сохраняются.
- «О нас» продолжает использовать отдельное представление.
- Старый маршрут категорий сохраняет перенаправление на `/{city}/menu/{category}`.
- Неизвестные slug обрабатываются как 404, а не как успешная пустая страница.
- Динамический маршрут не перехватывает статические и вложенные маршруты города.

## Результат этапа планирования

Исследование, инвентаризация маршрутов, предлагаемая архитектура, риски, проверки и вопросы для согласования находятся в `PLAN.md`.
