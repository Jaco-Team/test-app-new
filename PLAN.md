# PLAN: динамические текстовые страницы сайта

## Резюме

Убрать необходимость добавлять отдельный файл Next.js для каждой обычной текстовой страницы. Общий маршрут должен получать slug из URL и загружать соответствующую страницу через уже используемый `get_page_info` API.

Важная особенность: буквально добавить `pages/[city]/[page].jsx` рядом с существующим `pages/[city]/[category].js` нельзя — это два динамических маршрута для одного сегмента URL. Нужно заменить/объединить текущий динамический маршрут категорий с обработчиком текстовых страниц, сохранив его перенаправление категорий в меню.

Рекомендуемая граница: обычные CMS-страницы используют общий шаблон, страница «О нас» остаётся отдельным маршрутом и представлением, а интерактивные/специализированные экраны не переводятся на текстовый шаблон.

## Что проверено в коде

### Источник данных и повторение

- Проект использует Next.js Pages Router (`next` 16.3.6); динамические сегменты задаются именем файла в квадратных скобках. Локальная документация Next.js: `node_modules/next/dist/docs/02-pages/03-building-your-application/01-routing/02-dynamic-routes.md`; [официальная документация](https://nextjs.org/docs/pages/building-your-application/routing/dynamic-routes).
- Текущие отдельные текстовые маршруты запрашивают данные по `city_id` и slug через `api('contacts', { type: 'get_page_info', ... })`; большинство затем отображает содержимое через `modules/pageText.js` и использует общий `Footer`.
- Дублируются SSR-загрузка города, текста страницы, ссылок подвала и категорий, а также клиентская синхронизация состояния города/корзины.
- «О нас» — исключение по представлению: `pages/[city]/about.jsx` загружает `page: 'about'`, но показывает отдельный `modules/about/aboutPage`. То есть во frontend она тоже загружается через `get_page_info`, а не напрямую читает БД. Если под «данные берутся из БД» подразумевается иной источник или отдельное поведение, это нужно уточнить.

### Текущий динамический маршрут и конфликт

- `pages/[city]/[category].js` уже обслуживает произвольный одно-сегментный путь города: проверяет slug через `home.get_page_info`, распознаёт категорию по `category_id` (или slug `rolly`) и перенаправляет на `/{city}/menu/{category}`; всё остальное получает 404.
- Следовательно, добавление второго файла `[page]` рядом не является решением. Обработчик текстовых страниц и категории должны жить за одним динамическим сегментом.
- Файлы с фиксированными именами (`about.jsx`, `contacts.jsx`, `menu.jsx` и т. п.) и вложенные пути (`menu/[category].js`, `akcii/[name].js`) нужно сохранить с текущим приоритетом маршрутизации.

### Что не следует считать обычными текстовыми страницами автоматически

`contacts`, `document`, `about`, `menu`, `akcii`, `cart`, `profile`, `account`, `address`, `promokody`, `zakazy` и `sitemap` используют самостоятельные представления, состояние, авторизацию, структурированные данные или специальную навигацию. Их не следует переводить на общий текстовый рендер только потому, что они также получают данные через `get_page_info`.

## Предлагаемое решение

1. Заменить текущий общий файл `pages/[city]/[category].js` единым динамическим обработчиком с понятным именем параметра `[page]` (или оставить текущее имя параметра, если переименование создаёт избыточный churn). Не создавать второй sibling-файл для того же сегмента.
2. Нормализовать и проверить `city` и slug; исключить пустые значения и некорректные параметры до обращения к API.
3. Разрешать slug как CMS-текстовую страницу через `contacts.get_page_info`. При наличии страницы передавать данные в общий шаблон `PageText`, подвал и существующую инициализацию состояния.
4. Классифицировать текст и категорию по одному ответу `contacts.get_page_info`: `page.category_id > 0` (или legacy slug `rolly`) означает категорию и сохраняет permanent redirect (Next.js HTTP 308) в `/{city}/menu/{slug}`. Не делать второй запрос к `home`.
5. Для неизвестного slug вернуть Next `notFound`; `api()` обозначает транспортный/серверный сбой как `{ st: false }`, такой ответ не превращать в 404 и завершать SSR ошибкой 500.
6. Удалить отдельные route-файлы только для согласованных обычных текстовых страниц. Оставить `about.jsx` и специализированные маршруты.
7. Вынести только действительно общую SSR-подготовку в небольшой серверный helper, если она используется динамическим маршрутом; не строить универсальную CMS-абстракцию и не копировать весь backend-контракт во frontend.
8. Сохранить особые классы, `activePage`, structured data, городскую коррекцию внутренних ссылок и CTA через небольшой центральный конфиг особенностей. Новый стандартный slug должен работать с дефолтным шаблоном без добавления отдельного JSX-файла или записи в обязательный slug allowlist.

### Порядок разрешения slug (реализовано)

Ключевой риск — текущий динамический маршрут категорий. Предлагаемый порядок классификации:

1. Один раз запросить страницу по slug через `contacts.get_page_info`.
2. Если запись содержит положительный `category_id` либо slug равен `rolly`, перенаправить на `/{city}/menu/{slug}` с `permanent: true`.
3. Если запись существует и не является категорией, отобразить общий CMS-шаблон.
4. Если успешный ответ не содержит страницу — вернуть 404; если `api()` вернул `st: false`, не маскировать сбой под 404.

Проверка локального Laravel-кода показала, что `contacts` и `home` делегируют `get_page_info` одному источнику `Page::getPageInfo()`, а ответ страницы содержит `category_id`. Поэтому один запрос к `contacts` позволяет сохранить категорийный redirect без дополнительного round-trip.

## Зафиксированные ограничения реализации

- Визуальный DOM/layout и существующие классы сохраняются; CSS и файлы стилей не менять.
- Не менять адаптивные единицы, формулы, брейкпоинты, размеры, media queries и порядок блоков.
- Не менять содержимое `modules/pageText.js`, `components/footer.js` и специализированных UI, если это не требуется для передачи тех же props из общего маршрута.
- Сохранять стиль существующего Pages Router и `.jsx` страниц; TypeScript/FSD/Storybook переписывание не входит в объём.
- Крупные коммиты имеют вид `feat|fix|refactor|docs: короткое описание` (нижний регистр, без title case и длинного резюме).

## Решения и оставшиеся ограничения

1. Список из 12 route-файлов подтверждён как scope реализации; новые slug автоматически попадают в общий шаблон, если backend возвращает для них CMS-страницу. Нет обязательного allowlist.
2. `about.jsx` и его отдельное представление остаются без изменений; несмотря на CMS-запрос, это не обычная страница `PageText`.
3. Временный сбой CMS API (`st: false`) завершает SSR ошибкой, а не soft-404. В Next это 500, поскольку проект не содержит отдельного UX/контракта для 503 на уровне страницы.
4. Legacy category redirect сохранён как permanent redirect; локальный Next вернул HTTP 308 (это фактический статус для `permanent: true`). Поведение завершающего слеша не меняется.
5. `/contacts`, `/document` и остальные интерактивные маршруты остаются вне миграции.

## Риски и ограничения

- Динамический роут общий для текстовых slug и legacy-категорий; неверная классификация сломает deep links и SEO.
- Ошибка или пустой ответ API сейчас в отдельных файлах часто превращается в redirect на город. Для универсального route это может создавать soft-404 и скрывать сбой backend.
- HTML контента передаётся в `dangerouslySetInnerHTML`; единый маршрут не должен расширять набор недоверенных источников или менять текущую границу доверия.
- Страница «О нас» также использует CMS API; исключение относится к её отдельному представлению, а не к доказанно уникальному источнику данных.
- Общий маршрут в случае временного сбоя API вернёт серверную ошибку 500: отдельный пользовательский экран сбоя не входит в задачу.
- Существующие специальные CSS, schema, клиентское состояние и CTA должны быть учтены до удаления отдельных файлов.

## Решение на этапе исследования

Реализуется общий Pages Router маршрут, заменяющий `[category].js` и объединяющий CMS-текстовые страницы с текущим category fallback. Scope ограничен 12 маршрутами, уже использующими `modules/pageText`; About, интерактивные кабинеты и самостоятельные разделы остаются отдельными. Layout, визуальная структура, CSS и адаптивные единицы заморожены; браузерная регрессия ещё не подтверждена.
